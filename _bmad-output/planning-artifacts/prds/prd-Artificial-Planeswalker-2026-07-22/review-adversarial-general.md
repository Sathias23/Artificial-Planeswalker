# Adversarial Review — Companion App PRD (prd.md + addendum.md)

**Reviewed:** 2026-07-22
**Scope:** Material added or changed since `docs/companion-app-feature-brief.md` (which previously survived adversarial review): FR-18–FR-21, G5, SC-5, CM-1–CM-3, NFR-08, UJ-1, revised phasing, OQ-A/OQ-B deferrals, plus cross-cutting tensions introduced by the merge. Baseline brief content re-litigated only where a new addition destabilizes it.

---

## Findings

- **FR-12 / NG5 / CM-1 three-way contradiction on what companion tools return.** NG5 promises "MCP tools continue to return text results so agent workflows work identically without the app." CM-1 forbids tools from "dump[ing] payloads back into chat" — tools return compact text. FR-12 says an unreachable backend yields "a text result noting the app is not running." Pick two: if `companion_show_suggestions` returns only "app not running" when the backend is down, the workflow does *not* work identically without the app (the suggestions are lost — SC-3 arguably fails); if it echoes the suggestions as text to preserve the workflow, it violates CM-1's no-payload-echo rule. The PRD asserts all three without resolving which one bends. This is the contract the very first MVP tool must implement, and it is currently self-inconsistent.

- **SC-1's 250 ms is unachievable as written for its own headline scenario.** SC-1 demands a rendered suggestion panel *with card art* within 250 ms of tool-call completion, with no warm-cache precondition. But suggestions are, by definition, cards *not* in the current deck — precisely the cards least likely to be in the image cache. A cold suggestion push requires N round-trips to the Scryfall CDN, which no localhost budget can bound at 250 ms. Either SC-1 needs a warm-cache qualifier (making it much weaker than it reads), needs to define "rendered" as art-pending-with-placeholders (unstated), or it is a criterion the MVP will measurably fail on first use. NFR-05's latency clause ("event-to-render under 250 ms") has the same silent ambiguity about whether "render" includes image paint.

- **FR-19 never says which image size the grid uses, and the wrong reading kills NFR-05.** FR-19 lists `normal`/`large`/`png` as acceptable full-face sources for the P0 grid. Scryfall `png` files are roughly 1–2 MB each; a 100-card Commander grid at `png` is 100–200 MB of decode even with a warm disk cache — the 1 s render budget in NFR-05 is dead on arrival under that reading. At `normal` JPG it is plausible. A P0 requirement that spans a 20x performance range depending on an unstated choice is not a requirement; the size-per-context decision (grid vs. detail view) must be pinned in the PRD or explicitly delegated with the performance constraint attached.

- **Click semantics collide between FR-19 (P0, Phase 1) and FR-17 (P1, Phase 2).** FR-19 makes click-to-flip the Phase-1 click behavior for DFCs in the grid. FR-17 later makes click-anywhere open a detail view. When both ship: does clicking a DFC flip it or open the detail view? Nothing arbitrates. Worse, UJ-1 — the canonical journey — has Brad "click one to read its full oracle text," which is FR-17 behavior, deferred to Phase 2. The MVP as phased cannot deliver the PRD's own user journey. Either FR-17 belongs in Phase 1 or UJ-1 is overselling the MVP.

- **FR-18's deferral silently deletes the MVP's baseline panel behavior.** FR-18 bundles two things: "the agent panel shows the latest push" (baseline display semantics) and "session history" (the enhancement). The whole FR is P1 and phased to Phase 2. Consequence: no Phase-1 requirement anywhere states what the agent panel does when a second push arrives — replace? stack? ignore? The latest-push baseline must be extracted into a P0 requirement (or folded into FR-08) or the MVP panel's core behavior is formally unspecified.

- **FR-20 is a P0 requirement with no falsifiable acceptance criterion, verified only by SC-5's sole-judge taste test.** "Dark, game-adjacent," "subtle motion," "evoking Arena/Untapped.gg rather than utilitarian dashboards" — every operative term is aesthetic judgment. The sole verification mechanism is SC-5: "judged by Brad, the sole quality gate... no external playtest." A P0 blocks MVP release, so release now hinges on an unbounded, single-person, no-rubric gate — un-schedulable and unfalsifiable. At minimum SC-5 needs a concrete checklist (reference screenshots, a named comparison set, an enumerated motion inventory) so "done" is decidable. Also note SC-5 only gates "the deck view and suggestion panel" — the swaps and tier-list panels escape the quality bar entirely.

- **The risk table's mitigation for the under-delivered-polish risk points at a section that doesn't contain it.** "UX spec before implementation (see §12)" — §12 is Open Questions and contains only OQ-A (payload schemas) and OQ-B (TS codegen). There is no UX-spec open question, no UX-spec entry in phasing, no owner, no ordering constraint anywhere. The one mitigation for the feature's self-declared existential risk ("cool is the point") is a dangling reference to nowhere.

- **NFR-07 vanished from phasing while §1 claims the opposite.** The Overview promises "release-grade docs, install polish, and CI parity apply from the start," yet the Phasing section assigns NFR-07 (tooling parity: ruff, mypy strict, frontend eslint/vitest, CI) to no phase at all — Phase 1 lists NFR-01–04, 06, 08 only. NFR-08 was added to Phase 1 in this revision; NFR-07 was left orphaned. Either the phasing list is wrong or the Overview's "from the start" claim is.

- **CM-2's "no request storms on deck load" has no supporting requirement anywhere.** FR-04 mandates fetch-on-first-request with disk caching, but nothing — no FR, no NFR — requires the image proxy to throttle, serialize, or concurrency-cap its CDN fetches. A cold first load of a 100-card deck is, per the written requirements, 100 near-simultaneous Scryfall CDN hits: exactly the storm CM-2 forbids and exactly the "hotlink hammering" NFR-08 claims to avoid. Scryfall's guidance asks for ~50–100 ms between requests. A counter-metric with no implementing requirement is a wish, not a control. Add a rate-limit/concurrency requirement to FR-04 or NFR-08.

- **CM-1 and OQ-A's deferral are circularly dependent.** CM-1 requires "negligible latency and token overhead" — "negligible" is never quantified, so the counter-metric cannot detect a regression. Meanwhile OQ-A defers payload max sizes to design, but the addendum says those limits must be set so "CM-1 holds." A design decision is being asked to satisfy a metric the PRD never defined. Put a number on CM-1 (tokens per tool return, ms per call) or admit it is not a metric.

- **CM-3's "no new server-side session state anywhere" is false as written.** The companion backend — a server, running on the user's machine — necessarily holds cross-request state: the active deck (FR-07 sets it, FR-15 displays it after any refresh), live WebSocket registrations, session tickets, the auth token. CM-3 presumably means the *MCP* server, but "anywhere" invites an implementer to argue the backend may not remember the active deck — which would break FR-15 on refresh. Scope CM-3 to the MCP server explicitly, and while at it: the PRD never says where active-deck state lives or whether it survives a backend restart.

- **FR-18's history is unbounded and its hydration semantics are unspecified.** No cap on history entries; a long brewing session accumulates dozens of pushes, each hydrating card data and images. Revisiting an old push after the deck has changed re-renders against *current* card/deck data — is stale-context display acceptable? Multiple connected tabs (FR-06 broadcasts to all clients) each keep divergent in-browser histories while active deck is global — cross-tab behavior unaddressed. "Lightweight" is doing a lot of unexamined work.

- **The image disk cache has no size bound or eviction policy.** With FR-19 pushing full faces (including optional `png`) and per-face caching for DFCs, the cache grows monotonically with every card ever viewed. CM-2's "at most once per image+size" even implies the cache must never evict (an evicted-then-refetched image violates it as written), and there is no refresh path when Scryfall re-uploads corrected imagery. For a P0 feature writing arbitrarily to the user's disk, an unbounded, never-invalidated cache deserves at least one sentence.

- **NFR-08 covers Scryfall etiquette but ignores Wizards of the Coast entirely.** This app ships in a public release, displays full copyrighted card faces as its centerpiece, and FR-20 explicitly directs the aesthetic to "evoke Arena" — a WotC product. Scryfall's own guidelines require downstream projects to comply with the Wizards Fan Content Policy, and the PRD's legal posture stops at "Scryfall attribution in the footer." No mention of the Fan Content Policy notice, no caution about trade-dress proximity to Arena. For a project that already went through an identity-scrub before going public, this is a conspicuous omission.

- **SC-1 gates the MVP while the machinery to meet it is deferred to Phase 2.** Success criteria are not phased, so SC-1 (250 ms) reads as an MVP release criterion — yet the phasing explicitly parks "NFR-05 hardening" in Phase 2. The MVP can therefore ship while failing its own first success criterion, or SC-1 silently isn't an MVP gate; the PRD doesn't say which.

- **FR-20's motion requirement meets zero accessibility consideration.** A UI product PRD with mandated animation ("subtle motion on updates") and a dark-only theme contains no accessibility line at all — no `prefers-reduced-motion`, no contrast floor, nothing. Even a one-line NFR delegating a11y baseline to the UX spec would do; total silence in a "deliberate product, not a debug dashboard" is off-brand for its own bar.

- **UJ-1 contradicts itself and trades on unquantified language.** "At no point does he touch the browser to make anything happen" — two sentences after he clicks a card to read oracle text (and FR-19 adds click-to-flip). The deck view updates "within a beat" — the PRD elsewhere has real numbers (250 ms, 1 s); the journey should use them or nothing. Also, the journey's app-is-alive assumption leans on connection status the MVP won't have (FR-15 is Phase 2): if the backend has died, MVP-Brad discovers it only by noticing the view stopped moving.

- **FR-19 leaves DFC grouping and flip-state semantics open.** The grid groups by card type and feeds a mana-curve summary — which face's type line and mana value classify a DFC? Does flip state persist across re-renders triggered by `deck_changed` refetches? These are product-visible behaviors (a flipped grid snapping back on every deck edit would read as a bug), not architecture detail, and neither the FR nor the addendum touches them.

---

## Disposition note

The brief's core (architecture, security model, ID canon, phasing skeleton) remains sound and was not re-litigated. The merge added genuine value (WS ticket auth carried through, NFR-08, counter-metrics as a concept) but introduced the contract contradictions above — most acutely the FR-12/NG5/CM-1 triangle, the SC-1 cold-cache impossibility, and the FR-18 baseline-behavior gap — which should be resolved before design handoff, since design (OQ-A payload schemas, UX spec) is being asked to build directly on top of them.
