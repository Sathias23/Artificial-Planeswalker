### Detection note

`sprint_status.py detect-epic --epic 7` resolves the **numeric** epic 7 (deck-power assessment, retro'd 2026-07-18), not the companion epic `c7`. The completeness gate was therefore applied **by hand** against `sprint-status.yaml:689-696`: all seven `c7-*` keys read `done`, `pending_stories` is empty. Recorded so the reader knows this check ran and how.

**Whether this is a regression is undetermined, and the evidence to settle it no longer exists.** The limitation is structural in the copy on disk — `detect-epic` parses story keys with `int(m.group(1))` and composes `retro_key = f"epic-{selected}-retrospective"`, and `update --epic` is `type=int` — so it is a design property of this version, not a stray annotation. But:

- The skill tree is gitignored (`.gitignore:14, 17`), so there is no local history to diff.
- `_bmad/_config/manifest.yaml` keeps only the *current* version (`6.11.0`), overwritten on update. `installDate: 2026-07-06`, `lastUpdated: 2026-08-16T00:22`. No prior version is recorded anywhere.
- `sprint_status.py`'s mtime is **2026-08-13 16:33** — *after* the C6 retro document was written (2026-08-13 08:20) and after all five earlier companion retros. **No prior companion retro ran against this copy of the script.**
- No c1–c6 retro document mentions `sprint_status.py`, `--epic`, or hand-editing at all, so they record neither hitting this nor avoiding it.

So an earlier BMAD may well have handled `c`-prefixed epics; it may equally have been hand-written every time. R9 is worth doing either way — the gate is real today — but it should not be filed as "a 6.11 regression" without evidence.

## 8. Key takeaways

1. **A one-line fix deferred across two epics costs more than eight of the failures it prevents.** R5 has now been sighted eight times, including live in its own retrospective. The lesson is not "fix R5" — it is that prep items with a known one-line remedy should be executed at the moment they are ledgered, not scheduled into a prep window that then gets consumed by the two largest items on the list.
2. **The guard was updated; the sentence beside it was not.** Three epics running, the same class: `App.test.tsx`'s census pinned four regions correctly while `AgentView.tsx` and `EXPERIENCE.md` still said three. Executable claims stay true because they fail; prose claims rot silently. This is the argument C6 R7 has been making since C5.
3. **Deriving an enumeration beats listing one.** `test_deck_changed_wiring.py` AST-walks for repository writers instead of naming five tools, so the spec's phantom "update" verb costs nothing and a future tool cannot be forgotten. This is the pattern to reach for whenever an AC says "enumerated in test".
4. **c7-7 was planned as an acceptance walk and found five gaps.** The headline — that no test anywhere had watched a `deck_changed` travel from a mutation tool to a socket — existed because each half was proven in a different test. That is exactly the defect class a retrospective's boundary lens exists for, and the story found it first. Worth repeating: give the closing story of an epic a real planning pass, not a victory lap.
