## Intent

**Problem:** A suggestions, swaps, tier-list or groups push does not say which deck it is about, so after a deck switch or an edit the companion shows old advice as if it were about the deck on screen, and the confidence token reads as the app's own.

**Approach:** Each of the four push payloads gains an optional, caller-supplied `deck_id`. The UI keeps it on the view and its history entry, resolves the name and `updated_at` from the existing read-only `GET /api/decks`, labels the view and the entry with that deck's name, and marks the push stale when the deck changed after it was sent or a different deck is displayed. The confidence indicator is labelled as the agent's.

**Decisions (Brad, 2026-11-10):**
1. A `deck_id` absent from a loaded `/api/decks` answer is labelled "For a deck that is no longer saved" and marked stale; the push still renders, and the push tools do not validate the id.
2. Wording: label "For {deck name}"; badge "Stale"; reasons "The deck changed after this was sent." and "Not the deck on screen."; suggestion rows read "Agent confidence: {token}"; the swaps chip label is "Agent confidence".
3. The plan stays whole over the 1600-token guideline: one goal, and the epic requires contract, generated artifacts, skills and `plugin/` in the same PR.

## Boundaries & Constraints

**Always:** `deck_id` is optional, nullable, and refused when blank or over `_MAX_DECK_ID_LENGTH` (reuse `_NullableDeckId`). A push without it renders byte-for-byte as today. Push tools stay sessionless and stateless; no new backend route; the companion only reads (AD-2). The label follows the entry's own `deck_id`, never the active deck. `HISTORY_CAP`, `historyWith`, `openAgentView` revisit and retain semantics are unchanged. New user-facing strings live in `copy.ts` modules.

**Never:** a DB read or deck validation in the push tools; server-side session state; a schema change or migration; a new live region; hand-edits to `openapi.json`, `types.d.ts`, `static/` or `plugin/`; changes to `src/viewer/`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Other deck | push `deck_id=A`, B displayed | view and entry say "For A", marked stale: not the deck on screen | none |
| Edited since | push ts T, A's `updated_at` > T | marked stale: deck changed after it was sent; flips live on `deck_changed` | none |
| Fresh, same deck | push for A, A displayed, unedited | "For A", not stale | none |
| No deck_id | today's payload | no label, no stale marker, nothing fetched | none |
| Deck switch | push for A, then switch to B | history entry still "For A" | none |
| Unknown id | id absent from a loaded `/api/decks` | "For a deck that is no longer saved", marked stale | none |
| Summaries not loaded / read fails | before the first answer, or `unreachable` | no label yet; no stale claim | silent, next trigger retries |
| Bad wire value | `deck_id` blank, non-string or absent on a frame | treated as no `deck_id` | the builder folds it to `null` |

## Design Notes

The name and `updated_at` come from `GET /api/decks` (one cheap aggregate read, already shipped and read-only) rather than from the MCP tool. The tool is sessionless by design, and staleness needs the deck's *current* `updated_at`, which only a read at display time can give. The label is resolved live from the entry's own `deck_id`, so it survives a deck switch with no snapshot field. A refetch fires on each push carrying a `deck_id`, on `deck_changed` and on reconnect, and only once some push has carried an id, so a session that never sends `deck_id` makes no extra request. 8.4, 5.2 and 9.1 edit these files next, so the wire shape is one optional field per payload.
